# 预构建镜像与 love 管理菜单

用户部署只需下载 `love` 管理脚本。要求 Linux amd64 / arm64、Docker Engine 和 Docker Compose 2.24.4+，宿主机无需 Node.js、npm 或源码。

## 安装

在独立目录执行：

```sh
curl -fL https://raw.githubusercontent.com/kevinhuang001/love-app/main/love -o love
chmod +x love
./love
```

只有官方 GHCR 应用镜像 `ghcr.io/kevinhuang001/love-app:latest`，没有 Release 镜像或自定义镜像仓库选项。GHCR 包需为 Public，才能匿名拉取。首次运行从镜像中取出 Compose 与终端界面，选择数据库、监听 IP/端口、HTTP/HTTPS、证书及管理员凭据，保存到权限 0600 的 `.env` 后启动。运行规则在隐藏后台 `/#admin` 管理，详见 [配置边界](configuration.md)。

## 日常管理

运行 `./love`，方向键选择、回车确认，Ctrl+C 取消。菜单使用 Clack；重新显示前清屏，操作结果保留到按回车返回。

| 操作               | 行为                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 部署配置           | 修改 `.env`，包含数据库、监听、HTTPS、管理员凭据与高级部署项                                                      |
| 启动、停止、重启   | 选择必要的 Compose 覆盖文件，复用数据卷                                                                           |
| 状态与版本、日志   | 查看容器与镜像、最近 200 行日志                                                                                   |
| 更新软件及管理工具 | 查询 GHCR 元数据并比较当前运行镜像；没有新版本立即返回，有更新才备份、拉取固定 digest、更新 love 与菜单脚本并启动 |
| 备份、恢复         | 保存与恢复 `.env`、数据库及媒体，恢复前再备份当前状态                                                             |
| 卸载               | 默认保留数据；删除数据卷需要输入当前部署专属确认文字                                                              |
| 回滚上次更新       | 使用本地保存的上一个 GHCR 镜像，不回滚数据                                                                        |
| 刷新页面           | 清屏并重新读取部署状态                                                                                            |

更新只从 GHCR 下载镜像，并从镜像更新管理与代理脚本。Compose、`.env`、证书与数据保留；随脚本提供的 Caddy 代理模板会刷新并重启代理，避免旧模板继续限制上传大小。没有更新时不下载镜像层、不停止应用、不备份；检查失败明确报错，不误报“最新版本”。新版本下载和部署工具校验完成后才应用镜像引用。更新失败保留备份与回滚镜像。跨数据库结构版本回滚应同时使用对应的数据备份。

管理脚本、代理模板和 `.env` 的替换使用目标目录中的独立临时文件，写入完成后原子改名，失败清理临时文件。旧的 `love.next` / `.env.next` 文件、目录或悬空链接不会阻止更新，也不会被沿链接写入。更新脚本写入失败时，不切换应用镜像或修改部署配置；备份会恢复原先运行的应用。

## 跨数据库迁移与媒体清理

先更新软件及管理工具，再选择“SQLite → PostgreSQL”，配置内置或外部数据库并输入 `MIGRATE`。工具备份后暂停写入，迁移全部表和媒体，核对后切换配置。目标可已经初始化管理员及默认设置，但不得有用户、配对、媒体等业务数据；迁移会以源库的管理员和设置替换目标初始设置。`.env` 中的管理员凭据和媒体加密密钥保持不变。迁移报告位于备份目录的 `postgres-migration.json`，包含表行数、媒体数量和实际字节数，不含密码。

正常导入失败会回滚目标业务数据，原配置不变，原先运行的 SQLite 应用恢复。同一源快照再次执行会核对已完成迁移，不重复导入。目标服务启动失败时恢复原 SQLite 配置，已提交的目标数据保留；若原库后来又产生新数据，应选择新空目标库重新迁移，工具不会覆盖已完成迁移的目标。

迁移仅导入数据库引用的媒体，不导入历史垃圾文件。可先使用“清理 SQLite 未引用媒体”：备份后暂停写入，通过源 SQLite 完整性/关联检查才执行；保留 `media` 表引用的全部变体，即使尚未发布到相册或聊天。删除未引用的普通文件及上传临时文件，跳过符号链接和媒体根目录下未知子目录。已有备份仍保留清理前的文件。

## 备份文件

备份位于部署目录的 `backups/时间戳/`：`deployment.env`、`data.tar.gz`、PostgreSQL 的 `database.dump` 和 `SHA256SUMS`。PostgreSQL 的 `database.dump` 包含全部媒体二进制，`data.tar.gz` 只保留应用卷及可能尚未完成的临时文件；SQLite 的媒体仍在 `data.tar.gz`。备份包含密码、媒体密钥及私人媒体，请保存到安全位置，不要提交到 Git。

SQLite 在应用停止后备份数据卷。PostgreSQL 通过 PostgreSQL 18 的客户端镜像进行一致性 dump；外部数据库需要可从容器网络访问且账号具备 dump / restore 权限。love 停止自己的应用写入，外部数据库若还有其他写入程序，管理员应一并暂停，以保证数据库与媒体对应。

恢复只接受当前部署的备份，校验数据库类型、项目名和 SHA-256，并要求输入 `RESTORE`；覆盖前先保存当前状态。恢复失败时保持应用停止，防止继续向不完整数据写入。部署目录和备份仍保留，可排查后重新恢复。

## 镜像发布

主分支 CI 的 Web、SQLite、PostgreSQL、两种 Dockerfile、Android 全部通过后，在原生 amd64 / arm64 运行器构建并启动测试，然后推送 GHCR 并发布多架构 manifest。提供 latest/main 和 sha-完整提交标签；更新实际记录 digest。停止发布 Docker 镜像 Release 附件，Android APK 仍使用版本 Release。

Dockerfile 与 Dockerfile.cn 保留给开发者与 CI，用户只下载管理脚本和镜像。
