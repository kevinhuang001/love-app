# 独立 Love 管理程序与预构建镜像

管理工具使用 JavaScript + Clack，以 Bun 1.4.2 编译为独立二进制。用户无需安装 Bun、Node.js、npm 或下载源码。支持部署主机 Linux amd64 / arm64；应用通过 Docker Engine + Compose 2.24.4+ 部署。菜单、配置向导和数据库管理在宿主机运行，不再启动临时 UI、备份或数据库工具容器。

## 下载与目录

按 [README](../README.md) 从 GitHub Releases 下载对应架构的程序并校验 SHA-256，重命名为 `love`，在部署主机运行 `sudo ./love`。已有部署使用原目录；保留现有 `.env`、备份、证书和数据卷。仓库中的 `love` 仅是旧脚本迁移至二进制的一次性下载入口，新安装直接下载二进制。

程序以自身所在目录为部署目录，不使用当前工作目录。首次运行直接创建内嵌模板，尚未配置时也不需要拉取应用镜像。

| 路径                                        | 用途                                        |
| ------------------------------------------- | ------------------------------------------- |
| `love`                                      | 独立管理程序                                |
| `compose.yml`                               | 应用与数据卷定义                            |
| `compose.postgres.yml`                      | 选择内置 PostgreSQL 时使用                  |
| `compose.https.yml` / `compose.certbot.yml` | 选择内置 HTTPS / Certbot 时使用             |
| `compose.storage.yml`                       | 使用独立 PostgreSQL 工作卷时使用            |
| `Caddyfile` / `deploy/`                     | 代理与证书配置                              |
| `.env`                                      | 部署、连接、管理员凭据和签名密钥，权限 0600 |
| `backups/`                                  | 统一数据库备份                              |

宿主机程序直接读取本机 Docker 数据卷，通常需要 root 权限；远程 Docker context 不支持本地文件管理。内置 PostgreSQL 通过容器在 Linux bridge 上的地址连接，不向公网发布数据库端口；外部 PostgreSQL 使用当前 `.env` 的 URL，不启动内置服务。数据库和代理镜像不属于 Love 旧镜像清理范围。

## 日常管理

直接运行 `./love`，方向键选择、回车确认、Ctrl+C 取消。菜单刷新时清屏；操作结果保留到确认返回。无需二级指令。

| 操作               | 行为                                                              |
| ------------------ | ----------------------------------------------------------------- |
| 部署配置           | 创建或修改 `.env`，选择监听地址、端口、数据库、HTTPS 与管理员凭据 |
| 启动、停止、重启   | 选择对应 Compose 文件并复用数据卷                                 |
| 状态与版本、日志   | 查看容器状态、程序版本和日志                                      |
| 更新软件及管理工具 | 分别检查 GHCR 应用与 Release 管理程序；有变化才下载               |
| 数据库管理         | 一致性检查、备份、恢复和未使用媒体清理                            |
| 卸载               | 默认保留数据，删除数据卷需要输入专属确认文字                      |
| 刷新页面           | 清屏并重新读取部署状态                                            |

## 更新与镜像清理

镜像检查读取 GHCR 多架构索引、设备对应 manifest、配置摘要、正式版本及 OCI 源码 revision，识别 Docker config ID、containerd manifest ID、RepoDigests，以及同版本或同一源码的重复构建。不会把身份表示差异误报为软件更新。查询失败明确报错；镜像与管理程序的正式版本未同步时稍后再查，不应用不完整发布。

程序更新直接下载 Release 二进制并校验 SHA-256，在同目录写临时文件、同步后原子替换，再用 `execve` 重载自身。不会启动额外工具容器，也不会逐次遗留管理进程。应用更新只下载官方 GHCR 固定 digest；刷新对应发布的 Compose/代理模板，保留 `.env` 的部署值与数据卷。

新应用通过 Compose 健康检查后，清理本项目旧镜像，仅保留当前部署镜像。不提供版本回滚，不创建回滚标签或旧模板快照，也不自动切回旧镜像。镜像下载失败不会停止或重建原应用；应用启动失败时保留新版本配置，明确提示查看日志和修正配置后重新启动。未通过健康检查时跳过旧镜像清理。清理前检查所有容器，其他部署（包括停止的容器）使用的镜像及标签均保留；不强制删除、不进行全局 prune。成功更新后不再保留本地回滚镜像或回滚菜单。已是最新版时也可以通过更新操作清理旧版本遗留镜像。

更新、恢复、清理前备份均可选，默认跳过。未更新时不下载镜像层、不暂停应用、不创建备份。

## 数据库管理与备份

两种数据库继续使用相同统一格式：`backups/时间戳-随机值/deployment.env`、`data.tar.gz`、`SHA256SUMS`。压缩包包含 SQLite 数据快照、媒体与校验清单；PostgreSQL 媒体从 BYTEA 分块流式导出。打包和解包由 JavaScript 流实现，不调用宿主机 tar 或 PostgreSQL 客户端。

备份期间暂停本部署应用，结束或失败恢复原来的运行状态。SQLite 快照处理 WAL；PostgreSQL 使用 repeatable-read 快照。备份含密码和密钥，请保管好。外部数据库备份不会启动内置 PostgreSQL。

恢复自动支持 SQLite → SQLite / PostgreSQL、PostgreSQL → SQLite / PostgreSQL，也支持此前 SQLite 快照备份与无内层 manifest 的清理后备份。恢复仅使用备份携带的配置或数据库旧密钥解密，不依赖当前 `.env` 的旧值、不覆盖当前部署配置。无法解密凭据会列出并提供恢复其余内容的选项，头像和业务数据仍保留。旧 PGDMP 自定义备份需要先用旧版管理工具转换成统一数据包；新工具不启动临时数据库容器解码 PGDMP。

PostgreSQL 在一个事务中导入并核对全部业务表和媒体；失败回滚。SQLite 在目标卷暂存并通过持久化恢复日志切换，中断后回滚未完成切换。原备份只读，恢复前备份仍可跳过。

常规一致性检查验证关联、媒体存在、分块和容量，深入检查读取全部媒体并核对已存 SHA-256。清理先展示未使用记录、文件和容量，再确认删除；保护聊天、回忆、个人头像、AI 头像与历史消息头像，未发布上传全部纳入清理。清单变化时停止删除，已有备份不改动。PostgreSQL 删除空间可复用，物理文件不一定立即缩小。
