# 预构建镜像与 love 管理菜单

用户部署只需下载 `love` 管理脚本。要求 Linux amd64 / arm64、Docker Engine 和 Docker Compose 2.24.4+，宿主机无需 Node.js、npm 或源码。

## 安装

在独立目录执行：

```sh
curl -fL https://raw.githubusercontent.com/kevinhuang001/love-app/main/love -o love
chmod +x love
./love
```

只有官方 GHCR 应用镜像 `ghcr.io/kevinhuang001/love-app:latest`，没有 Release 镜像或自定义镜像仓库选项。GHCR 包需为 Public，才能匿名拉取。首次运行从镜像中取出 Compose 与终端界面，选择数据库、监听 IP/端口、HTTP/HTTPS、证书及管理员凭据，保存到权限 0600 的 `.env` 后启动。运行规则在隐藏后台 `/#admin` 管理，详见 [配置边界](configuration.md)。

## 日常管理

运行 `./love`，方向键选择、回车确认，Ctrl+C 取消。菜单使用 Clack；重新显示前清屏，操作结果保留到按回车返回。

| 操作               | 行为                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| 部署配置           | 修改 `.env`，包含数据库、监听、HTTPS、管理员凭据与高级部署项                                                |
| 启动、停止、重启   | 选择必要的 Compose 覆盖文件，复用数据卷                                                                     |
| 状态与版本、日志   | 查看容器与镜像、最近 200 行日志                                                                             |
| 更新软件及管理工具 | 查询 GHCR 元数据并比较当前运行镜像；没有新版本立即返回，有更新才拉取固定 digest、更新 love 与菜单脚本并启动 |
| 备份、恢复         | 保存数据库、媒体与密钥；恢复自动转换至当前数据库，保留当前 `.env`，恢复前可选备份当前状态                   |
| 卸载               | 默认保留数据；删除数据卷需要输入当前部署专属确认文字                                                        |
| 回滚上次更新       | 使用本地保存的上一个 GHCR 镜像，不回滚数据                                                                  |
| 刷新页面           | 清屏并重新读取部署状态                                                                                      |

更新只从 GHCR 下载镜像，并从镜像更新管理与代理脚本。Compose、`.env`、证书与数据保留；随脚本提供的 Caddy 代理模板会刷新并重启代理，避免旧模板继续限制上传大小。没有更新时不下载镜像层、不停止应用、不备份；检查失败明确报错，不误报“最新版本”。新版本下载和部署工具校验完成后才应用镜像引用。更新失败保留备份与回滚镜像。跨数据库结构版本回滚应同时使用对应的数据备份。

管理脚本、代理模板和 `.env` 的替换使用目标目录中的独立临时文件，写入完成后原子改名，失败清理临时文件。旧的 `love.next` / `.env.next` 文件、目录或悬空链接不会阻止更新，也不会被沿链接写入。更新脚本写入失败时，不切换应用镜像或修改部署配置；备份会恢复原先运行的应用。

更新、恢复和清理操作前均可选择“直接继续，跳过备份”（默认）、“先备份，再继续”或取消操作。跳过备份不会创建备份目录或复制媒体；手动选择“备份数据与配置”仍执行完整备份。恢复校验、PostgreSQL 事务回滚和 SQLite 中断恢复与此选项独立。

## 切换数据库与恢复备份

在“数据库管理”中选择“备份数据与配置”或“恢复备份”，无需单独迁移菜单。在原部署备份，随后通过部署配置选择 SQLite、内置或外部 PostgreSQL；也可以在新部署完成初始化后，把备份目录复制到新部署的 `backups/` 下。选择“恢复备份”并输入 `RESTORE` 即可。

自动识别备份内容，支持 SQLite → SQLite、SQLite → PostgreSQL、PostgreSQL → SQLite、PostgreSQL → PostgreSQL。项目名和数据卷可不同；恢复使用当前数据库、连接地址和应用卷，不把备份中的部署配置覆盖到当前 `.env`。管理员账号、监听地址、HTTPS、镜像和当前密钥均保留；AI Key 和 SMTP 密码在导入前重新加密为当前密钥。当前数据库可已有内容，确认恢复后用备份替换业务内容；尚未完成的图形/邮箱验证码在密钥不同的情况下作废，需要重新获取。

## 备份文件

备份位于 `backups/时间戳-随机值/`：`deployment.env`、`data.tar.gz` 和 `SHA256SUMS`。两种数据库使用同一数据包：SQLite 数据快照、数据库引用的全部媒体和带来源类型、行数、实际字节数及 SHA-256 的清单。PostgreSQL 媒体流式从数据库导出，恢复到 PostgreSQL 时流式写入数据库，恢复到 SQLite 时落盘；不重新压缩或转码。

备份暂停本部署的应用写入；PostgreSQL 使用只读 repeatable-read 快照，SQLite 私有快照同时处理 WAL。新备份流程直接使用应用镜像，不需要下载 PostgreSQL 客户端镜像，外部部署不会启动内置数据库。备份包含密码、密钥和私人媒体，请安全保存，不要提交 Git。

已有 SQLite `data.tar.gz` 及 PostgreSQL `database.dump`（PGDMP 自定义格式）备份可自动识别。旧 PGDMP 需要 PostgreSQL 解码，管理脚本仅为此启动隔离的临时读取容器，并在结束后删除容器、临时数据库卷和网络；不会把原生 dump 直接恢复到正式数据库。这是旧备份的读取过程，与当前选择外部数据库无关。应用只支持 SQLite / PostgreSQL 备份，不导入其他数据库产品的任意 SQL 文件。

恢复先校验备份再要求确认，覆盖前可选择另存当前状态。PostgreSQL 在一个事务中替换全部业务表及媒体分块，逐表及逐文件核对后提交；失败回滚，提交响应丢失时核对恢复凭据。SQLite 在目标卷暂存完整数据库和媒体，再通过持久化恢复日志切换；中断时启动先回滚未完成切换。原备份始终只读。恢复后应用启动失败时保留已恢复数据和恢复前安全备份，可检查日志后重启。

“数据库管理”统一提供一致性检查、备份、恢复与清理。常规检查验证数据库关联、媒体存在性、数据库分块和容量记录；深入检查完整读取媒体，并核对已存的 SHA-256。检查不修改业务数据，期间暂停应用，结束或失败均恢复原来的运行状态。

“清理未使用媒体”支持 SQLite 与 PostgreSQL：所有未进入聊天或回忆的上传、临时文件与未绑定分块均纳入清理，正在使用的个人和 AI 头像保留。先预览记录、文件与容量，再确认永久删除；清单变化时停止删除。备份可选，旧备份不修改。PostgreSQL 删除后的空间可复用，物理数据库文件不会立即缩小。
